# ADR-0135. 에이전틱 자동화·외부 작업·하이브리드 일꾼을 BPM의 세 기둥으로 세우고, NowView의 일반 부분은 통합 일꾼으로 들이고 업무 코드는 Company1로 보낸다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 (2026-11-08) |
| 날짜 | 2026-11-08 |
| 관련 | 계약 C11·C13·C14·C15, [ADR-0010](0010-service-apps.md)(서비스 앱·수행 모드), [ADR-0028](0028-replay-memory.md)(재생), [ADR-0102](0102-calling-outside-is-pull.md)(Pull), [ADR-0114](0114-remove-ui-automation.md)(UI 자동화 걷음), [ADR-0122](0122-consumer-folder.md)(일꾼 폴더), [ADR-0129](0129-product-folders.md)(제품 폴더), 참고 문서 「Camunda BPM 및 Agentic Automation 종합 가이드북」(2026-11, IT 아키텍처본부) 3·4·5장 |

## 배경

참고 문서는 BPM 엔진 위 자동화를 세 장으로 정리한다. **3장 에이전틱 자동화**는 서비스 태스크가 업무 문맥을 AI 오케스트레이터에 넘긴다. 오케스트레이터는 지식 검색 → 문맥 분석 → 추론·결정 → 도구 실행을 거쳐 결과를 돌려주고, 배타 게이트웨이가 그 결과로 길을 가른다. **4장 External Task Worker**는 엔진이 일감을 토픽 큐에 올린다. 일꾼은 Lock & Fetch로 가져가 수행하고 Complete를 보내며, 실패하면 백오프로 다시 한다. **5장 하이브리드 자동화**는 AI 분석·API 호출·RPA(UI 조작) 세 종류의 일꾼을 한 오케스트레이션 층에서 조율한다. 장애가 나면 오류 경계와 **트랜잭션 보상**이 앞선 단계를 되돌린다.

BPM은 이 셋 중 4장을 이미 갖고 있다(C15). 나머지 둘은 조각으로만 있다. AI 태스크(엔진 안)와 서비스 앱(LLM 앱)은 있지만, **AI 일꾼이 지켜야 할 모양**(지식 검색·검증·누가 어느 판으로 불렀는가)은 정해지지 않았다. API 일꾼(어댑터 일꾼)은 있다. RPA 일꾼은 ADR-0114로 걷었고 **보상은 엔진에 없다**.

한편 NowView는 바깥 저장소에서 이 셋을 가장 많이 쓰는 일꾼이다. 회사 BPM 프로세스의 서비스 태스크를 C15로 가져가 규칙 계산·회사 시스템 읽기/쓰기·Agent 초안(검증된 LLM 초안)을 한다. 그런데 옛 이름의 엔진(`chaeksas-core` git 고정)에 묶여 있고, 일꾼 호스트·토픽 라우팅·Agent 검증 같은 **일반적인 뼈대**가 장면 코드와 한 덩어리다. 그래서 BPM의 다른 일꾼이 그 뼈대를 쓸 수 없다.

장면 코드(약 3만 줄)는 가상 부품사 한 곳의 **업무 규칙**이다(규칙 계산·경영 기록·장면별 Agent 초안). 그 회사의 BPMN 원본(`bpm/`)·각본(`scenarios/`)·회사 시스템은 이미 Company1 저장소에 있다. NowView 화면은 역할이 세 번 바뀌었고(10-26·10-31·11-03) 업무 화면은 이미 Company1로 갔다 — 과도기의 산물이다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. **일반 부분은 BPM, 업무 코드는 회사 저장소** — BPM에 통합 일꾼(일꾼 호스트·종류 셋·AI 작업 뼈대·일꾼 콘솔)을 세우고, 장면 코드는 Company1의 업무 처리기로 옮겨 BPM 패키지를 바깥에서 쓴다. NowView는 걷는다 | 세 장이 BPM의 일반 기능이 된다. 플랫폼에 특정 회사의 업무 규칙이 들어오지 않는다(확장을 import하지 않는 규칙·「모의 앱은 제품이 아니다」와 같은 결). **실제 고객과 같은 모양**이라 BPM이 「바깥에서 쓸 수 있는가」를 시험받는다. 업무 규칙이 그 BPMN·회사 시스템과 한 저장소에 모인다 | BPM 계약이 바뀌면 Company1이 따라 고친다(실제 고객과 같은 비용). BPM 패키지를 바깥에서 받을 길이 필요하다 |
| B. 장면 코드까지 BPM으로 (`server/nowview`) | 계약 변경을 같은 PR에서 받는다 | 플랫폼 저장소에 한 회사의 업무 규칙 3만 줄과 시험이 들어온다. 바깥 사용이 시험되지 않는다 |
| C. NowView는 그대로, 의존만 BPM 패키지로 | 이사가 없다 | 일반 뼈대가 NowView 안에 갇히고, 업무 코드가 그 BPMN과 다른 저장소에 남는다 |

토픽 모델도 두 길이 있었다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 가. **토픽 = 앱 id 유지 + 일꾼 종류 칸** (`kind: ai \| api \| rpa`) | C15의 「불러도 되나」 검사(토픽 = 확장 id ↔ 배포된 C1의 요구)가 그대로다. 화면이 종류로 묶어 보이면 문서의 세 큐와 같은 그림이 된다 | 종류별 큐가 물리적으로 따로 있지는 않다 |
| 나. 토픽 = 일 종류 (`ai-request`·`api-call`·`rpa-task`) | 문서와 글자 그대로 같다 | 권한·manifest 검사를 작업 단위로 다시 짜야 한다. 한 토픽에 여러 앱의 작업이 섞여 「누가 이 작업을 맡는가」가 흐려진다 |

## 결정

**A + 가.** 세 장을 BPM의 세 기둥으로 이름 붙이고 각각의 자리를 아래처럼 정한다. NowView의 일반 부분은 **통합 일꾼**으로 들이고, 업무 코드는 Company1 저장소의 **업무 처리기**가 된다. 그 뒤 NowView는 걷는다.

### 1. 문서의 낱말 ↔ BPM의 낱말

| 문서 | BPM | 비고 |
| --- | --- | --- |
| External Task, 토픽 큐 | 외부 작업(C15), 토픽 | 토픽은 앱(확장) id다 |
| Lock & Fetch / Complete / 백오프 재시도 | `consumers/fetch`(잠금) / `complete`·`fail` / C14 `retry`(부르는 쪽이 `attempt`를 올려 새 일감) | 이미 있다 |
| 워커 | **일꾼** | 용어집 §금지어 — 「워커」를 쓰지 않는다 |
| 통합 워커 | **통합 일꾼** (`unified_consumer`) | 새 용어 |
| AI 분석 워커·API 호출 커넥터·RPA 워커 | **일꾼 종류** `ai`·`api`·`rpa` | 새 칸 |
| AI 오케스트레이터 (서비스 태스크 안의 AI 에이전트) | **AI 작업** — `kind: ai`인 작업. 엔진 안의 AI 태스크와 다르다 | 새 용어. 화면에서 「에이전트」를 쓰지 않는다 |
| 트랜잭션 보상 | **보상** (BPMN compensation) | 새 용어, C14에 들인다 |

### 2. 기둥 하나 — 외부 작업 (4장)

C15를 그대로 둔다. 바꾸는 것은 **종류 칸 하나**다.

- C11 `Operation`과 C13 작업에 `kind`(`ai` | `api` | `rpa`)를 더한다. 비우면 C13 HTTP 어댑터 작업은 `api`이고 나머지는 `ai`다. **선택 칸이라 판을 올리지 않는다**(원칙 3).
- C15 `LockedTask`·`ExternalTaskInfo`에 그 작업의 `kind`를 싣는다. Center는 manifest에서 읽어 붙이고, 부르는 쪽이 지어낼 수 없다.
- CON-01 실행 상세의 「외부 작업」에 「종류」 열을 둔다(화면 문서 먼저). 토픽 표는 콘솔에 없으니(ADR-0122) 일꾼 콘솔(§4)이 종류로 보인다.
- 일꾼 쪽 백오프는 지금처럼 두지 않는다. 다시 부르는 것은 부르는 쪽 C14 `retry`가 정하고, 일꾼은 `retryable`만 말한다. 문서의 「사전 정의된 백오프 재시도 정책」이 C14 `retry`다.

### 3. 기둥 둘 — 에이전틱 자동화 (3장): AI 작업

AI 작업은 **서비스 태스크(`bpm:serviceCall`)가 부르는 `kind: ai` 작업**이다. 통합 일꾼의 **AI 작업 뼈대**(`bpm.unified_consumer.ai`)가 문서의 다섯 단계를 이렇게 고정한다.

| 문서의 단계 | AI 작업 뼈대 | 지키는 것 |
| --- | --- | --- |
| 1. 문맥 전달 | 일감 `input` = 그림이 넘긴 변수. 뼈대가 작업의 `input_schema`로 검사한다 | 그림에 없는 값을 지어내지 않는다 |
| 2. 지식 검색·문맥 분석 | **지식 원천**(`KnowledgeSource` 인터페이스 — 파일 폴더·벡터 저장소·회사 시스템). 찾은 조각마다 **근거 id**가 붙는다 | 근거 id 없는 지식은 넘기지 않는다 |
| 3. 추론·결정, 도구 실행 | `bpm.llm`으로 모델을 부른다. 도구는 작업이 적은 것만 쓴다(AI 태스크의 허용 도구와 같은 규칙) | 숫자는 만들지 않는다 — 계산은 규칙(도구)이 하고 모델은 인용만 한다 |
| 4. 검증 | 출력 스키마, **근거 id가 실제로 찾은 것인가**, **본문의 숫자가 입력·도구 결과와 맞는가**(작업이 대조할 칸을 적는다) | 하나라도 어긋나면 그 응답을 버린다. 정해진 횟수만큼 다시 묻고, 그래도 안 되면 실패한다 |
| 5. 결과·결정 반환 | 출력 = 작업 `output_schema`(게이트웨이가 읽을 `decision` 칸을 권한다) + `provenance{agent_id, agent_version, execution_id, model_called, prompt_version}` | 「모델을 실제로 불렀는가」를 출력이 말한다 |

**수행 모드와의 관계**(원칙 7, ADR-0010)는 이렇게 맞춘다.

- 운영 실행(결정 수행)에서도 AI 작업은 모델을 부른다. 다만 **작업 정의가 `kind: ai`로 그 사실을 드러내고**, 출력은 검증을 지나야 하며, 실패하면 오류 경계로 간다. 이것은 「LLM을 **몰래** 부르지 않는다」와 어긋나지 않는다. 그림을 그린 사람이 AI 작업을 골랐기 때문이다. 결정 수행의 정의 「LLM 없이(**또는 최소로**)」의 「최소로」가 이 자리다.
- **자율 수행으로 넘어가는 폴백은 그대로 없다.** AI 작업이 검증에 실패하면 `TaskFailed`다. 그림은 오류 경계 + 사람 결재(재검토)로 받는다. 문서 그림의 「No(재검토)」 갈래가 그 모양이다.
- 시험 러너 셋(`mock` 결정론 · `llm` · `fail`)을 뼈대가 준다. 업무 예제와 인수 시험은 `mock`으로 돈다(모델의 똑똑함이 아니라 맞물림을 본다).

엔진 안의 **AI 태스크**(재생·도구 차례)는 그대로 둔다. 둘의 차이는 이렇다. AI 태스크는 실행하는 쪽(Studio·PC)의 도구로 일하고, 재생 명세를 남겨 결정 수행에서 모델을 줄인다. AI 작업은 일꾼 쪽의 지식·회사 시스템으로 일하고, 매번 검증한다.

### 4. 기둥 셋 — 하이브리드 자동화 (5장): 통합 일꾼과 보상

**통합 일꾼**(`bpm-unified-consumer`, `server/unified_consumer`)은 일꾼 프로세스 하나가 여러 토픽과 세 종류를 함께 맡는 것이다. 문서의 「통합 워커 오케스트레이션 레이어」는 BPM에서 **엔진 + Center**다. 통합 일꾼은 그 아래에서 종류별 처리기를 한 프로세스에 묶을 뿐 흐름을 쥐지 않는다.

- **업무 처리기**(`handler_package`)는 엔트리 포인트 `bpm.consumer_handlers`로 찾는다. 하나가 토픽 몇 개와 작업마다의 처리 함수를 준다. 확장과 같은 규칙으로 통합 일꾼 코드는 특정 업무 처리기를 import하지 않는다. 「확장」(C13 — 그림·Studio에 기여하는 것)과 다르다: 업무 처리기는 일꾼 안에서만 돈다.
- **종류 `ai`**: AI 작업 뼈대(§3) 위의 처리기.
- **종류 `api`**: 외부 확장 정의를 어댑터 일꾼과 **같은 코드**(`bpm.adapter_consumer`)로 통합 일꾼 안에서 돌린다. 업무 처리기 없이 정의만 주면 어댑터 일꾼과 같다 — `bpm-adapter-consumer`는 그 모양으로 남는다.
- **종류 `rpa`**: **자리만 만든다** — 종류 값, C15·화면의 표기, 처리기 인터페이스, 시험용 가짜 RPA 일꾼. 실제 화면 조작과 「RPA 일꾼이 어느 PC에서 도는가」(PC 실행기와의 관계, ADR-0014)는 UI 자동화를 다시 들일 때 정한다(ADR-0114).
- **일꾼 콘솔은 서비스 앱 콘솔(SVC-00~03)이다** — 새 웹 앱을 만들지 않는다. 통합 일꾼이 서비스 앱과 같은 관리 API(C11 `/admin/v1/status`·`usage`)를 내고 작업 줄에 `topic`·`kind`를 싣는다. 그래서 보이는 것은 **어느 회사든 같은 것**(맡은 토픽·작업별 종류·최근 24시간 호출·오류율·사용 기록)이다. BPM 프로세스별 진행은 Center 콘솔(CON-01·02)이, 회사별 업무 지표는 그 회사의 화면(Company1 사이트)이 보인다.

**보상**은 C14와 엔진에 들인다.

- 활동에 **보상 경계 이벤트**(`compensateEventDefinition`)를 달고, 연관(association)으로 **보상 처리기**(`isForCompensation="true"`인 활동)를 잇는다.
- **보상 던지기**(중간 던지기 이벤트·종료 이벤트의 `compensateEventDefinition`)가 울리면 엔진은 같은 범위에서 **끝난 활동** 중 보상 처리기가 달린 것을 **끝난 순서의 거꾸로** 하나씩 돌린다. `activityRef`가 있으면 그 활동만 돌린다. 끝나지 않은 활동은 보상하지 않는다.
- 문서의 「RPA·API 장애 → 오류 경계 → 앞선 단계 되돌리기」는 **오류 경계 → 보상 던지기 종료 이벤트**로 그린다. 그래서 오류 경계와 보상은 서로 다른 일을 한다. 오류 경계는 「어디로 갈지」를 정하고, 보상은 「무엇을 되돌릴지」를 정한다.
- 보상 처리기도 서비스 태스크라 C15 일감이 된다. 멱등 키의 `node_id`는 처리기 노드다.
- C14 검사에 규칙을 더한다. 보상 처리기는 흐름(sequence flow)을 받거나 내지 않는다. 보상 경계에는 연관이 하나만 있다. 던지기의 `activityRef`는 같은 범위의 보상 가능한 활동이어야 한다.
- 재생·되살리기: 보상을 몇 번째까지 돌렸는지를 실행 상태에 적는다. 다시 뜨면 남은 것부터 돈다.

### 5. NowView 나누기

| NowView의 것 | 갈 곳 |
| --- | --- |
| 일꾼 호스트(`consumer.py`의 토픽 → 처리기, `routed_by` — BPM 프로세스 id로 회사·업무 찾기), 일꾼 파일(`worker_file.py`) | BPM `server/unified_consumer` (`bpm.unified_consumer`) — 일반화한다 |
| Agent 러너·검증(`sc01/agent.py`·`sc02/agent.py`의 공통 부분) | BPM `bpm.unified_consumer.ai` (AI 작업 뼈대) |
| 회사 설정(`config.py`)의 일반 부분 — BPM 프로세스 id → 업무 처리기 매핑 | BPM `bpm.unified_consumer` 설정 |
| 대시보드의 일반 부분(일꾼 일감) | 서비스 앱 콘솔로 보는 통합 일꾼 (BPM 진행은 Center 콘솔) |
| 장면 코드 sc01~07·s2·s3·platform, 회사 시스템 연결(`company.py`), 따라가기(`follower.py`), 경영 기록(`records.py`), 장면별 Agent 지시문·검증 칸, 확장 정의 `external.extension.json`, 그 시험 | **Company1 저장소의 업무 처리기** (예: `Company1/worker`, 엔트리 포인트 `bpm.consumer_handlers`) |
| 대시보드의 회사별 지표 | Company1 사이트 |

- **Company1은 BPM 패키지를 바깥에서 쓴다** — 지금 NowView처럼 이 저장소의 커밋에 고정한 git 의존(`subdirectory`)으로 `bpm-contracts`·`bpm-service-kit`·`bpm-unified-consumer`를 받는다. 업무 처리기는 이 패키지들의 **공개 면**(엔트리 포인트·처리 함수 모양·AI 작업 뼈대)만 쓴다 — 그래서 그 면이 바뀌면 판을 올리고 변경 이력에 적는다.
- 「회사 사이트는 계산하지 않는다」(NowView `docs/role-split.md`)는 그대로다 — 업무 처리기는 사이트가 아니라 따로 도는 일꾼 프로세스다.
- NowView의 Postgres는 업무 처리기의 작업 상태 저장소로 함께 간다. Center 저장소(SQLite, ADR-0070)와 섞지 않는다.
- **옮기는 동안 NowView 저장소를 얼린다.** 옮김이 끝나면 NowView는 걷고 저장소는 읽기 전용으로 둔다. `www.nowview.work`를 어떻게 할지(일꾼 콘솔로 돌리기·내리기)는 운영 반영 때 따로 묻는다.
- **이 저장소에는 Company1 코드가 들어오지 않는다.** BPM 쪽 시험은 시험용 업무 처리기(`tests/fake_handlers.py` — `tests/fake_extension.py`와 같은 결)로 돈다.

## 결과

- 쉬워지는 것: 문서의 세 장이 BPM의 이름 붙은 기능이 된다(외부 작업·AI 작업·통합 일꾼 + 보상). 플랫폼에 특정 회사의 업무 규칙이 없다. 다른 회사의 업무 일꾼도 업무 처리기 하나로 붙고, Company1이 그 첫 바깥 사용자로서 공개 면을 시험한다. 서버가 셋(BPM·NowView·회사)에서 둘(BPM·회사)로 준다. Agent 검증 규칙(숫자 대조·근거 id·provenance)이 모든 AI 작업의 규칙이 된다.
- 어려워지는 것·포기하는 것: BPM 계약·공개 면이 바뀌면 Company1이 따라 고친다(같은 PR로 못 받는다). 장면 코드를 Company1로 옮기는 일은 그대로 크다. 토픽별로 물리적인 큐를 나누는 Camunda식 배치는 하지 않는다(종류는 칸으로만 가른다). RPA는 이름만 있고 실제로 돌지 않는다.
- 다시 볼 조건: ① 한 앱의 작업이 종류별로 다른 일꾼에게 나가야 할 때(같은 토픽을 종류로 나눠 가져가기 — C15 `fetch`에 `kinds` 거르기). ② UI 자동화를 다시 들일 때(RPA 일꾼의 자리·PC 하나 규칙). ③ 업무 처리기의 공통 부분이 회사마다 되풀이될 때(그 부분을 BPM 공개 면으로 올리기). ④ git 고정 의존이 버거워질 때(사내 패키지 저장소).
