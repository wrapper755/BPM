# ADR-0175. 작업공간을 프로젝트로 묶는다 — 회사는 프로젝트의 속성이다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-11-20 |
| 관련 | 계약 C17(작업공간)·C16(조직), 화면 CON-20, [ADR-0143](0143-design-happens-in-the-console.md)(작업공간 하나 = BPM 프로세스 한 벌 — 그대로 산다), [ADR-0048](0048-installing-shared-packages.md)(공유 BPM 프로세스는 설치해서 부른다), [ADR-0125](0125-organization-and-work-placement.md)(회사 > 부서 > 직원) |

## 배경

Company1의 BPM 프로세스 16개(공통 2 + 업무 14)를 콘솔로 옮기려고 들였더니 **작업공간 16개가 한 줄로**
섰다. 저작 홈에는 무엇이 한 회사의 한 일에 속하는지 말할 자리가 없고, 회사는 작업공간마다 따로 적힌다.

사용자가 2026-11-20에 「프로젝트 내에 n개의 프로세스가 있는 형태」를 요청했다 — **한 회사가 프로젝트를 여럿
한다**, 그러니 회사는 프로젝트의 속성이면 된다. 작업공간 하나는 지금도 그대로 BPM 프로세스 한 벌이고,
그 위에 **묶는 층**이 없다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. **프로젝트를 묶는 층으로만** 둔다 — 짓기·판·배포는 프로세스마다 | 패키지·배포·실행기 계약(C1·C5·C12)이 그대로다. Company1처럼 장면마다 판이 다른 일에 맞는다 | 프로젝트를 한 번에 배포하는 길은 없다 |
| B. 프로젝트 하나 = 판 하나 = 패키지 하나 | 한 번에 짓고 배포한다 | 패키지가 프로세스 여럿을 담게 되어 C1·C5·C12·실행기·설치가 모두 바뀐다. 한 프로세스를 고쳐도 전부의 판이 오른다 |
| C. 작업공간 안에 프로세스 여럿 (작업 폴더 하나에 진입 정의 여럿) | 파일을 함께 쓴다 | ADR-0143 §1(한 벌 = 한 프로세스)을 뒤집는다. 검사·시험·짓기가 「어느 진입」을 늘 물어야 한다 |

## 결정

**A다.** 프로젝트는 **프로세스(작업공간)를 묶는 층**이고, 짓기·판·검사·시험 실행·배포는 지금처럼 프로세스마다다.

1. **프로젝트** = `id`·`name`·`description`·**`company`**. id 규칙은 작업공간과 같다(`^[a-z0-9][a-z0-9._-]{0,63}$`).
   프로젝트는 파일이 없어 **DB가 원본**이다(작업공간의 설계 값은 여전히 `process.json`이 원본이다).
2. **회사는 프로젝트가 정한다.** 프로세스는 만들 때 프로젝트를 고르고 회사를 물려받는다. 회사는 만든 뒤
   바뀌지 않는다(C16 — 작업공간이 지금 그렇다). 작업공간 행의 `company`는 **프로젝트에서 베낀 값**으로 남긴다
   — 회사로 거르는 모든 자리(C16 범위)가 그 칸을 본다. 둘이 갈라지지 않게 하는 것은 「회사는 바뀌지 않는다」와
   「옮기기는 같은 회사 안만」 두 규칙이다.
3. **프로세스는 같은 회사 안에서 프로젝트를 옮길 수 있다** (`PATCH /workspaces/{id}`의 `project`). 다른 회사
   프로젝트로는 못 옮긴다(422 `company_mismatch`) — 회사가 바뀌면 이미 지은 패키지와 갈라진다.
4. **공유 BPM 프로세스는 따로 프로젝트에 둔다**(사용자 결정). 부르는 쪽은 지금처럼 **배포된 판을 설치한다**
   (ADR-0048) — 같은 프로젝트에 있어도 파일을 바로 가리키지 않는다. 가리키게 하면 시험한 그림과 지은 패키지가
   다른 것을 부른다.
5. **가져오기는 프로젝트에 한다** — 옛 작업 폴더 zip 하나, 또는 **작업 폴더 여럿을 담은 zip 하나**
   (Company1 `bpm/company1/` 통째)를 받아 **프로세스 여럿을 한 번에** 만든다. id는 각 `process.json`의 것이다.
   하나라도 못 들이면(같은 id·경로 규칙·`libs/` 사본) **아무것도 만들지 않는다**. `libs/` 사본은 경로 규칙으로
   막지 않고 **버린 뒤 기록의 `libs`를 응답에 돌려준다** — 콘솔이 「공유 프로세스 설치」로 잇는다.
6. **이미 있는 작업공간은 회사마다 프로젝트 하나로 옮긴다**(34판) — 프로젝트 id는 회사 id, 이름은 회사 이름이다.
   프로젝트를 고르지 않고 만든 작업공간도 그 프로젝트로 간다(지금의 자동화·시험을 깨지 않는다).
7. **비지 않은 프로젝트는 지우지 않는다**(409 `not_empty`). 프로세스를 지우면 배포된 패키지는 그대로이듯,
   프로젝트를 지운다고 프로세스를 함께 지우지 않는다.

화면은 저작 홈이 **프로젝트 카드**가 되고(CON-20a), 프로젝트 하나를 열면 **프로세스 표**(CON-20c)다. 편집기
(CON-20b)는 그대로이고 지금 자리 줄과 탐색기가 프로젝트를 안다.

## 결과

- 쉬워지는 것: 한 회사의 일을 프로젝트로 나눠 본다. Company1 같은 묶음을 zip 하나로 들인다. 회사가 프로세스마다
  흩어지지 않는다.
- 어려워지거나 포기하는 것: 프로젝트 단위 배포·판은 없다(B). 프로젝트 안 프로세스끼리도 공유 프로세스는 설치해서 부른다.
- 다시 볼 조건: 프로젝트 안 프로세스를 늘 함께 배포해야 하는 일이 나오면 B를 다시 본다. 프로젝트마다 권한을
  나눠야 하면(지금은 회사까지만) C16에 프로젝트 자리를 더한다.
