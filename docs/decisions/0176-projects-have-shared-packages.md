# ADR-0176. 프로젝트마다 「공통 패키지」 칸이 있다 — 공통 패키지 목록은 「라이브러리」 묶음으로

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-11-20 |
| 관련 | 계약 C17, 화면 CON-00 [M]·CON-06·CON-20, [ADR-0175](0175-projects-hold-processes.md) §4(**대체한다**), [ADR-0169](0169-shared-packages-belong-to-authoring.md)(**메뉴 자리를 대체한다**), [ADR-0151](0151-console-follows-the-lifecycle.md)(묶음 여섯 → 일곱), [ADR-0048](0048-installing-shared-packages.md)(설치해서 부른다 — 그대로) |

## 배경

ADR-0175는 공유 BPM 프로세스를 **따로 프로젝트**에 두었다(Company1의 공통 둘 → 「공통 BPM」 프로젝트). 화면에서 보니
「공통 BPM」이 업무 프로젝트와 나란히 카드 하나로 서서, 어느 일의 공통인지 말하지 못했다. 사용자가 2026-11-20에
「프로젝트마다 기본 공통 패키지가 있는 것으로」 하자고 했다. 함께 「저작 › 공통 패키지」(지어 올린 공통 패키지 목록,
CON-06)는 새 묶음 「라이브러리」 아래로 옮기자고 했다 — 프로젝트 안의 공통 칸(만드는 자리)과 회사의 목록(쓸 것을
고르는 자리)이 한 묶음에 있으면 같은 이름이 두 번 선다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. **작업공간에 종류(`kind`)를 둔다** — 프로젝트 화면이 종류로 두 칸을 가른다 | 짓기 종류가 자리에서 정해진다(지금은 짓는 순간 고른다). 프로젝트·회사 규칙이 그대로 | 작업공간 표에 칸 하나 |
| B. 프로젝트마다 숨은 「공통」 하위 프로젝트 | 표가 그대로 | 프로젝트가 둘씩 생기고, 옮기기·지우기 규칙이 하위 프로젝트를 알아야 한다 |
| C. 지은 패키지만 프로젝트 화면에 보인다(저작은 지금처럼) | Center가 그대로 | 공통을 만드는 자리가 여전히 따로다 — 요청과 다르다 |

## 결정

**A다.** 작업공간 하나는 **업무 프로세스**(`bpm_process`) 아니면 **공통 패키지**(`process_lib`)다. 프로젝트 화면은
두 칸이고, 모든 프로젝트에 「공통 패키지」 칸이 처음부터 있다(비어 있을 수 있다).

1. **종류는 C1 `kind`와 같은 낱말이다** (`bpm_process`·`process_lib`). DB가 원본이다(작업공간 행의 칸 — 35판).
   `process.json`에는 쓰지 않는다 — 옛 작업 폴더에 그 칸이 없고, 종류는 그림이 아니라 **프로젝트 안의 자리**다.
   만들 때·가져올 때 정하고, `PATCH`로 바꿀 수 있다(칸 사이를 옮긴다). 이미 지은 패키지는 그대로다.
2. **짓기는 작업공간의 종류를 따른다** — 「배포 후보로 만들기」에서 종류를 고르지 않는다. `POST …/package`의
   `kind`를 비우면 작업공간의 종류다(적으면 지금처럼 그 종류 — 자동화를 깨지 않는다).
3. **공통 패키지를 부르는 길은 그대로 설치다** (ADR-0048) — 같은 프로젝트 안이어도 파일을 바로 가리키지 않는다.
   설치 목록은 **같은 회사면 어느 프로젝트의 것이든** 뜬다(사용자 결정 — 프로젝트는 어디서 만들었는지를 말할 뿐이다).
4. **「공통 BPM」 같은 따로 프로젝트는 두지 않는다**(ADR-0175 §4를 대체). 쓰는 프로젝트의 공통 칸에 둔다.
5. **메뉴는 일곱 묶음이다** — 대시보드 › 저작 › **라이브러리** › 배포 › 운영 › 연결 › 권한·조직. 「라이브러리」에는
   「공통 패키지」(CON-06) 한 줄이라 펼치지 않고 바로 간다. 「저작」도 「프로젝트」 한 줄이 되어 바로 간다
   (ADR-0169의 자리를 대체 — 「배포가 아니다」는 그대로다).

## 결과

- 쉬워지는 것: 어느 일의 공통인지 프로젝트가 말한다. 짓는 사람이 종류를 잘못 고를 일이 없다.
- 어려워지거나 포기하는 것: 여러 프로젝트가 함께 쓰는 공통은 한 프로젝트에 놓아야 한다(설치는 어디서나 된다).
  위 막대 묶음이 일곱이라 좁아지는 폭이 조금 넓어진다.
- 다시 볼 조건: 프로젝트마다 공통 패키지를 숨겨야 하면(지금은 회사 범위) 설치 목록을 프로젝트로 거른다.
  「라이브러리」에 줄이 더 생기면(예: 도구 정의) 그때 펼친다.
