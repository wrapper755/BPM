# ADR-0139. 일꾼의 종류는 Center 관리자가 정하고, 일꾼은 그 종류의 일감만 가져간다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-11-09 |
| 관련 | 계약 C15(§가져가기, §일꾼 관리 `ConsumerInfo`·`ConsumerCreateRequest`·`ConsumerUpdateRequest`), C11·C13 작업 `kind`, 화면 CON-17·CON-01, [ADR-0135](0135-agentic-automation-and-unified-consumer.md)(일꾼 종류 — 「다시 볼 조건 ①」), [ADR-0137](0137-consumers-are-managed-in-the-console.md), [ADR-0122](0122-consumer-folder.md) |

## 배경

일꾼 종류(`ai`·`api`·`rpa`)는 일꾼이 아니라 **작업**에 붙어 있다(ADR-0135). 일꾼은 이름·토픽·토큰뿐이라 CON-17 「일꾼」에서 어느 일꾼이 AI 작업을 맡고 어느 일꾼이 외부 API를 부르는지 알 수 없었다. 프로그램을 종류마다 따로 띄워도(LLM 서비스 앱·어댑터 일꾼·통합 일꾼) Center에게는 같은 「토큰 + 토픽」이고, 한 앱의 작업을 종류마다 다른 프로그램에 나눠 줄 길도 없었다 — ADR-0135가 「다시 볼 조건 ①」로 남긴 자리다.

드러난 구멍이 둘 더 있었다.

- Center는 일감의 `kind`를 **일꾼이 올린 서비스 앱 manifest**에서만 읽었다. 외부 확장 토픽은 manifest가 없어 일감의 종류가 늘 비었다 — HTTP 어댑터 작업은 `api`뿐인데도(C13 E3).
- CON-17 「맡은 앱」은 manifest만 보였다. 외부 확장 정의를 올린 어댑터 일꾼은 「—」로 보여 아무것도 올리지 않은 일꾼과 구별되지 않았다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 맡은 토픽에서 끌어내 보이기만 한다 — 토픽의 manifest·외부 확장 정의에 적힌 작업 `kind`를 모은다 | 새 저장 칸·새 규칙이 없다 | 아직 아무것도 올리지 않은 일꾼은 「모름」이다. 관리자가 정할 수 없고, 한 앱의 작업을 종류로 나눌 수 없다 |
| B. **일꾼에 종류를 두고 Center 관리자가 정한다. 가져가기를 그 종류로 거른다** | 관리자가 콘솔에서 일꾼의 역할을 정하고 바로 보인다. 한 앱의 작업을 종류마다 다른 일꾼에게 나눌 수 있다 | C15 가져가기·DB·화면이 바뀐다. 정한 값과 토픽의 작업이 어긋날 수 있다(→ 경고로 보인다) |
| C. 이름 규칙만 쓴다(`ai-…`·`api-…`) | 바꿀 것이 없다 | Center가 모른다. 지키는지 아무도 보지 않는다 |

## 결정

**B** (사용자 결정, 2026-11-09). A로 먼저 만들어 본 뒤 「관리자가 정하고 고칠 수 있어야 한다」로 바꿨다 — A의 끌어내기는 **어긋남 경고**의 재료로 남는다.

1. **일꾼은 종류를 여럿 가진다**(`ai`·`api`·`rpa` 중 하나 이상 — 통합 일꾼은 여럿을 함께 맡는다). Center 관리자가 CON-17의 「새 일꾼...」·「편집...」에서 체크박스로 정한다. C15 `ConsumerCreateRequest`·`ConsumerUpdateRequest`의 **`kinds`**, Center 저장소 26판 `consumers.kinds_json`.
2. **가져가기는 그 종류의 일감만 준다.** 일감의 `kind`가 일꾼의 종류에 없으면 같은 토픽이어도 내주지 않는다. **종류를 모르는 일감**(`kind`가 빈 것)은 종류와 상관없이 나간다 — 지어내지 않고, 막지도 않는다. 일꾼이 보내는 `FetchRequest`는 그대로다(Center가 일꾼 행에서 읽는다).
3. **종류를 정하지 않은 일꾼**(`kinds`가 없다 — 일꾼 폴더로 들어왔거나 이 판 전에 만든 일꾼)은 지금처럼 **모든 종류**를 가져간다. 화면은 「정하지 않음」이고 「편집...」에서 정한다. 콘솔에서 만들 때는 하나 이상 고른다. API에서 `kinds`를 비우면(빈 목록·빠짐) 만들기는 「정하지 않음」, 편집은 「그대로」다.
4. **토픽의 종류**(끌어낸 것)는 그 토픽의 작업들이 가진 `kind`의 모음이다. 근거는 일감에 종류를 붙일 때와 같다 — ① 일꾼이 올린 서비스 앱 manifest, ② 없으면 등록돼 있고 철회되지 않은 외부 확장 정의(같은 id는 나중에 등록된 판). C15 `ConsumerInfo.topic_kinds`(토픽 → 종류, 아는 토픽만).
5. 일감을 올릴 때(C15 §올리기) ②도 본다 — 외부 확장 토픽의 일감에도 그 작업의 `kind`(`api`)가 붙는다. 정의에 그 작업이 없으면 종류가 비어 있을 뿐 거절하지 않는다(외부 확장 작업의 대조는 어댑터 일꾼이 한다 — 지금과 같다).
6. CON-17 「종류」 열은 **정한 종류**다. 토픽의 종류 가운데 일꾼이 맡지 않는 것이 있으면 값 옆에 ⚠와 툴팁(「external은 API 작업이 있는데 이 일꾼은 API를 맡지 않습니다 — 그 일감을 가져가지 않습니다.」)을 둔다. 막지는 않는다 — 다른 일꾼이 그 종류를 맡을 수 있다.
7. `ConsumerInfo.apps`에 그 일꾼의 토픽에 **일꾼이 올린 외부 확장**(철회되지 않은 것 중 나중에 등록된 판 하나, `id@version`)도 넣는다.

## 결과

- 이 결정으로 쉬워지는 것: CON-17에서 일꾼의 역할이 바로 보이고 관리자가 고친다. 한 앱의 AI 작업과 API 작업을 서로 다른 일꾼이 가져가게 할 수 있다. 외부 확장 일감도 CON-01 「종류」가 찬다.
- 어려워지거나 포기하는 것: 종류를 잘못 정하면 그 일감은 아무도 안 가져가 기한에 `no_consumer`로 실패한다 — 화면의 ⚠가 그 자리를 알린다. 일꾼 폴더 파일(`FolderConsumer`)에는 종류 칸이 없다 — 들인 뒤 콘솔에서 정한다(ADR-0137 「처음 들이기만」과 같은 결).
- 다시 볼 조건: 일꾼 폴더로 첫 설치하는 배포가 종류까지 정해 들어와야 할 때 — `FolderConsumer.kinds`를 둔다.
