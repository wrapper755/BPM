# ADR-0167. 쪽 번호는 열 개씩, 한 쪽 줄 수는 고르고, 큰 목록은 서버가 쪽을 자른다

| 항목 | 값 |
| --- | --- |
| 상태 | 수락 |
| 날짜 | 2026-11-20 |
| 관련 | 화면 CON-00 [A]·[B]·CON-01·CON-04, [ADR-0166](0166-top-bar-header-and-ten-rows.md)(§1 글자 13·§3 10줄 — **이 결정이 바꾼다**), [ADR-0165](0165-lists-filter-as-you-go-and-page.md)(쪽은 주소에 싣지 않는다 — **큰 목록만 바꾼다**) |

## 배경

ADR-0166을 입힌 결재함을 보고 사용자가 셋을 말했다.

1. **「10」은 줄 수가 아니라 쪽 번호의 수였다** — 「1 2 … 104」가 아니라 쪽 번호가 열 개 보이기를 바랐다.
2. **한 쪽에 보일 줄 수를 고를 수 있게.**
3. **위 막대의 묶음 글자(13)가 작다** — 막대는 화면의 제목 줄이다.

그리고 **결재함이 늘 느리다**고 했다(인덱스를 의심했다). 재 보니 Center는 결재 1,032건을 0.33초에 준다. 느린 것은 콘솔이다 — `DataTable`이 받은 줄을 **전부 서버에서 그려**(표 줄 + 휴대폰 카드, 두 벌) 브라우저로 보내고 브라우저가 열 줄만 보였다. 결재함 한 장의 HTML이 **8.3MB**였고, 개발 서버에서 그리기 35~85초·하이드레이션 1분이 걸렸다. 「담당」 후보를 고르려고 같은 결재 목록(1.7MB)을 한 번 더 받기도 했다.

## 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| 쪽 나누기를 브라우저에 두고 줄 수만 고른다 | 바뀌는 것이 적다 | 받은 줄을 다 그려 보내는 것이 그대로다 — 느린 까닭이 남는다 |
| Center API에 `limit`·`offset`을 더한다 | 받는 양까지 준다 | 계약(C5·C6)이 바뀐다. 받는 것은 0.33초라 지금 막힌 곳이 아니다 |
| **큰 목록은 콘솔 서버가 쪽을 자르고 쪽은 주소에 싣는다** | 보내는 양이 한 쪽뿐이다. 계약이 그대로다 | 쪽을 넘기면 서버에 다시 묻는다. 목록 화면이 주소의 `page`·`size`를 넘겨야 한다 |

## 결정

1. **쪽 번호는 열 개씩 묶어 보인다** — 지금 쪽이 든 묶음(1–10, 11–20 …)의 번호 열 개와 「맨 앞」·「앞」·「뒤」·「맨 뒤」. 「…」는 없다.
2. **한 쪽 줄 수는 고른다** — 10·20·50·100, 기본 **20**(ADR-0166 §3의 10을 되돌린다). 쪽 단추 왼쪽 「1–20 / 1032」 옆의 고르는 칸이다. 고르면 첫 쪽이다.
3. **큰 목록은 콘솔 서버가 쪽을 자른다** — `DataTable`의 `paging`(주소의 `page`·`size`)을 받은 목록은 **그 쪽의 줄만** 그리고 쪽 단추는 링크다. 결재함(CON-04, 다 받는다)과 실행 기록(CON-01, 500건까지)이 쓴다. 나머지 목록(100건 아래)은 브라우저에서 나눈다 — 한 화면에 표가 여럿이라 주소의 `page`가 겹치는 화면이 있다(ADR-0165). 결재함은 「담당」 후보를 위해 목록을 두 번 받지 않는다 — 거르지 않았으면 받은 목록을 쓴다.
4. **위 막대의 글자는 14(`body`)다**(ADR-0166 §1의 13을 바꾼다) — 묶음·배지·계정·단추가 같다. 「BPM」은 16 굵게(`bold`), 앱 타일 24 그대로.

## 결과

- 결재함 한 장이 한 쪽(20줄)만 싣는다. 쪽을 넘기면 서버에 다시 묻는다(Center 0.3초 + 그리기).
- 큰 목록이 새로 생기면 `paging`을 넘기는 것을 잊지 않는다 — 잊어도 돌지만 다 그려 보낸다.
- Center가 결재를 다 주는 것(1.7MB)은 남는다. 수만 건이 되면 C6에 `limit`을 더한다.
